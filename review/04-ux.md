# UX and accessibility

Scope note: the keyboard story for the *core* writing loop is strong — a rebindable command registry, a command
palette, a quick switcher with proper arrow-key handling and `aria-selected`, a real focus trap on modals, a
`prefers-reduced-motion` block in the stylesheet, and `:focus-visible` rules rather than blanket `outline: none`.
The findings below are the surfaces that fell outside that.

Several items here are interaction *defects* and are written up fully in `01-bugs.md`; they are cross-referenced
rather than repeated.

---

### [High] The file explorer is the one primary surface that cannot be operated from the keyboard

**Where:** `src/renderer/src/components/FileTree.tsx:332-515` (`TreeRow`, `FolderRow`, `FileRow`)
**Trigger:** Try to open a note from the sidebar without a mouse.
**Detail:** Tree rows are plain `<div>` elements carrying `onClick`, `onContextMenu`, `onDragStart` and
`onDrop`, with no `tabIndex`, no `role`, and no `onKeyDown`:

```tsx
<div className={`tree-row file${isActive ? ' is-active' : ''}`}
     onClick={(e) => openNote(path, { newTab: e.ctrlKey || e.metaKey })}   // :451-458
```

`tabIndex` appears exactly once in the whole renderer (`WidgetFrame.tsx:100`), and no command in the registry
focuses the explorer. This is specific to the tree: the backlinks panel, outline, starred pane, tag pane, tab bar
and search results all use real `<button>` elements and are reachable.

**Impact:** Keyboard and screen-reader users cannot browse the vault structurally at all. The quick switcher
(Ctrl+P) covers "open a note I can name", but not browsing, renaming, moving, or any of the ten context-menu
actions. Folder expand/collapse is unreachable. There is also no accessible tree semantics — a screen reader sees
an undifferentiated stack of text.
**Fix:** Give the tree `role="tree"` / `role="treeitem"` with `aria-expanded` and `aria-level`, adopt roving
`tabIndex` (one row focusable at a time), and handle Up/Down/Left/Right/Enter. Virtuoso complicates this — the
focused row can be unmounted by scrolling — so the roving index needs to live in the store, not the DOM. Add a
`view.focusExplorer` command so there is a way in.
**Confidence:** Verified.

### [Medium] Context menus cannot be reached or driven with the keyboard

**Where:** `src/renderer/src/components/ContextMenu.tsx:38-67`
**Trigger:** Open any context menu, then try to choose an item without a mouse.
**Detail:** The markup is correct (`role="menu"`, `role="menuitem"`, real `<button>`s, Escape closes) but
nothing focuses the menu when it opens, and there is no arrow-key handling. The menu is rendered at the end of
`App`'s tree, so tabbing from the element that opened it walks the entire rest of the page first. There is also
no keyboard route to *open* one — no `Shift+F10` / ContextMenu-key handler anywhere.
**Impact:** Every action that lives only in a context menu — rename, duplicate, change icon, change colour, pin,
copy link, reveal in explorer, delete — is mouse-only. Some have command-palette equivalents; icon, colour and
pin do not.
**Fix:** Focus the first item on open, handle Up/Down/Home/End/Enter/Escape, and restore focus to the opener on
close. `useModalTrap` already has most of this machinery.
**Confidence:** Verified.

### [Low] Toasts stack without a cap or deduplication

**Where:** `src/renderer/src/store/uiStore.ts:162-167`
**Trigger:** Any burst of errors — e.g. a vault on a disconnected network share, where several notes fail to
save at once, or the external-change toast firing for a batch of files.
**Detail:** `pushToast` appends unconditionally and schedules a 3.2 s / 6 s removal per toast. There is no cap on
the array and no collapsing of identical messages. `editorStore.save` (`:141`) toasts per failed path, and
`externalChange` (`:249`) toasts per changed path.
**Impact:** A `git checkout` touching twenty dirty notes produces twenty stacked error toasts, which can cover
the window for six seconds.
**Fix:** Cap the list (drop the oldest past ~4), and collapse repeats into a count.
**Confidence:** Verified.

### [Low] Live-preview task checkboxes have no accessible name

**Where:** `src/renderer/src/editor/livePreview.ts:115-131` (`CheckboxWidget.toDOM`)
**Detail:** The widget creates a bare `<input type="checkbox">` with a class and a checked state — no
`aria-label`, no associated label. The surrounding task text is a separate text node that the checkbox is not
linked to. The codebase does this correctly elsewhere (`extensions.ts:84` sets `aria-label` on the editor
content; `HrWidget` at `:144` sets `aria-hidden`), so this is an omission rather than a policy.
**Impact:** A screen reader announces "checkbox, not checked" with no indication of which task.
**Fix:** `box.setAttribute('aria-label', <the task line's text>)` — the line is already read at `:124` for the
click handler.
**Confidence:** Verified.

### [Low] Quick Note's undo and redo buttons are unreliable by construction

**Where:** `src/quicknote/main.ts:100` (`editor.value = active.text` in `render`), `:315-322` (undo/redo buttons)
**Detail:** The toolbar buttons call `document.execCommand('undo' | 'redo')`, which is deprecated and only
affects edits that themselves went through the execCommand path or native typing. `render()` assigns
`editor.value` directly, which **clears the textarea's native undo stack** — so switching drafts, closing a
draft, or completing a save silently empties the history behind the buttons.

The file shows awareness of this: `duplicateCurrentLine` (`:232`) deliberately uses
`document.execCommand('insertText', …)` specifically to preserve undo, with a manual `.value` fallback.
**Impact:** Undo works sometimes and not others, with no visible rule. Worse than an absent feature.
**Fix:** Either keep a small explicit undo stack per draft alongside the text, or reconstruct the textarea when
swapping drafts rather than assigning `.value` (so each draft keeps its own native history).
**Confidence:** Verified.

### [Low] Search scope silently follows the active note

**Where:** `src/renderer/src/components/SearchPanel.tsx:19-20`, `:56`
**Detail:** `currentFolder` is derived from the active tab and is in the search effect's dependency array. With
"This folder" enabled, switching to a note in a different folder re-runs the search against the *new* folder
without any signal beyond the tooltip text changing. The filter chip still just reads "This folder".
**Impact:** Results change underneath the user for a reason that is not visible.
**Fix:** Show the resolved folder name on the chip when it is active, or pin the scope at the moment it is
switched on.
**Confidence:** Verified.
